## 优化 WSL 轮询卡顿（用户反馈：项目一多、3s 轮询导致窗口特别卡）
- 根因：旧 `setupWslPoller.snapshot()` 每个 WSL 项目每轮 = 1 次 `wsl.exe ls` + 每个 `.env*` 一次 `wsl.exe cat`（全 `execSync` 同步阻塞）。项目多 → 主线程被大量同步 `execSync` 持续占用 → 主进程来不及响应渲染进程 HTTP 请求 → 窗口卡。
- 修法（electron-main.js）：
  1. **批量单次调用**：改 `snapshot()` 为异步（`execAsync`），一次 `wsl.exe bash -c` 在 Linux 侧 `ls` 列举 `.env.*` 并对每个候选 `md5sum`，返回「文件名|md5」；子进程数从 `(1+N)/项目/轮` 降到 `1`。
  2. **异步不阻塞**：`execSync` → `execAsync`（`promisify(exec)`），主线程不再被卡。
  3. **防重叠**：`inFlight` 标志，上一轮未跑完跳过本轮，避免 wsl.exe 调用堆积。
  4. **错峰启动**：按 `hashStr(projectId)` 稳定错峰初始延迟，避免启动瞬间所有 WSL 项目同时触发首轮、瞬时拉起一堆 wsl.exe。
  5. **默认间隔 5000 → 10000ms**（WSL 非实时，10s 足够且更省）；范围仍 [500,600000]。失败保护：wsl.exe 整体失败返回 null，保留 prev、不误触发变更。
- 前端无需改逻辑（设置界面只写范围）；仅把 App.jsx:295 注释"不必等 3 秒轮询"改为"不必等轮询周期"。
- 重新打包：`NODE_OPTIONS="" npm run electron-build` → `release/EnvSwitch-0.1.0-Setup.exe`、`win-unpacked/EnvSwitch.exe`。`node --check` 通过。

## 修复 WSL 轮询命令失败（用户截图反馈：`Command failed: wsl.exe -d ... bash -c '...'`）
- 根因：`snapshot()` 用字符串形式 `execAsync(cmd)` 调用，在 Windows 上经 `cmd.exe` 解析；单引号在 cmd.exe 里不是特殊字符，被当字面量传给 bash → bash 收到 `-c "'<script>'"`（含外层单引号）→ 试图执行一个名字带引号的命令 → 报错。
- 修法：改用数组形式 `execAsync('wsl.exe', ['-d', distro, 'bash', '-c', script])`，绕过 cmd.exe，参数原样传递给 wsl.exe → bash 正确收到脚本内容。
- **二次报错**：`The "callback" argument must be of type function. Received an instance of Object` —— 根因：`execAsync = promisify(exec)`，而 `exec` 签名是 `(command, options, callback)`，首参必须是字符串命令，**不支持数组**；把数组当首参传进去后，第二个位置的 options 被当成回调 → 报错。
- **正确修法**：改用 `execFile`（签名 `(file, args[], options, callback)` 天然支持数组 args 且不经 shell 解析），定义为 `execFileAsync = promisify(execFile)`，`execFileAsync('wsl.exe', ['-d', distro, 'bash', '-c', script], {...})`。execFile 同样绕过 cmd.exe（且比 exec 数组更安全：不经 shell，无注入风险）。
- **重大发现**：上一轮 `ccOqAQ` 这次 execFile 版打包**实际失败了**（之前用 `| tail -8` 截断没发现），`release/` 产物仍停在 16:39 的「exec 数组版」（即会报 `callback must be function` 的那版）。用户跑的就是这个没升级的 exe，所以才会看到"没执行/没日志"。
- **加诊断日志**：runCheck 每轮打 `[WATCHER] WSL 轮询触发 ${projectId}`；snapshot 成功打 `[WATCHER] WSL 快照成功 ${projectId}: N 行`。重新打包（完整输出写 /tmp/envswitch_build.log，不再截断），确认 EXIT=0 且产物时间戳更新。
- **用户反馈「连日志都没有、实测没执行」根因**：跑的 exe 是 16:39 的旧版（exec 数组版，每轮 runCheck 调 exec 数组 → 同步抛 TypeError `callback must be function` → 被 catch 捕获本应打「WSL 轮询失败」；若用户看到的真完全没有日志，则更可能是没重装最新 exe 或 exec 数组版在某些 Node/electron 下异常未走到 log）。无论如何，必须先确保最新 exe 真正覆盖。

## 修复 WSL 快照「收到 0 行」—— execFile 返回空 stdout（用户截图反馈第二轮）
- 用户截图铁证：所有 WSL 项目每轮 `raw stdout: len=0, Head=""`，但无报错（execFileAsync 不 throw）、脚本内容正确、路径解析正确。
- **根因**：`execFile` + 数组形式通过 `CreateProcess` 直接调用 `wsl.exe` 时，进程 exit code 0 但 stdout 完全空。推测是 wsl.exe 在非 shell 环境（无 cmd.exe 中转）下的输出行为差异。
- **修法**：改回 `execAsync`（字符串形式，经 cmd.exe），用**双引号包裹脚本**+ 内部 `"` 用 `""` 转义（cmd.exe 双引号内转义规则）：
  - `const escapedScript = script.replace(/"/g, '""');`
  - `const cmd = \`wsl.exe -d ${distro} bash -c "${escapedScript}"\`;`
  - cmd.exe 正确剥离外层双引号 → wsl.exe 收到干净脚本 → bash 正常执行有输出
- 这避开了两个之前的坑：① 单引号被 cmd.exe 当字面量 ② execFile 数组导致 wsl.exe 空 stdout。
- 保留诊断日志（快照脚本内容 + raw stdout 长度/前 200 字符），便于后续验证。
- **20:18 双引号版有 bug**：`execAsync` 根本没定义（顶部只定义了 `execFileAsync`），运行时 snapshot 会抛 ReferenceError；且方案本身脆弱（依赖 cmd.exe `""` 规则）。用户质疑"是否最佳方案"合理。
- **最终修法（stdin 方案，20:38 版）**：彻底绕开"参数传脚本"的所有坑——`execFileAsync('wsl.exe', ['-d', distro, 'bash', '-s'], { input: script, ... })`。脚本由 `options.input` 经 stdin 原样传给 `bash -s`（POSIX 标准从 stdin 读命令），不经 cmd.exe、无引号/转义、不塞命令行参数。这是"Windows 侧调 WSL 执行脚本"的标准稳健做法，无兼容性隐患。

## 「使用中」匹配增强：md5 + 文件名决胜负（用户："用md5+文件名，避免有些文件内容一模一样"）

  **注意**：此字段**仅作并列决胜负**，不参与"无 md5 匹配时兜底"——故手动改 .env（md5 无匹配）仍不高亮，不会重蹈早期假阳性覆辙。
